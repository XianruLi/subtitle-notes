## 通用 — Python Daemon开发

- [2026-06-26] Windows文件锁定与日志Handler清理
  - **现象**：测试中使用 `TemporaryDirectory` 做日志文件测试时，cleanup阶段抛出 `PermissionError`
  - **原因**：Windows对打开的文件持有排他锁，`TimedRotatingFileHandler` 未显式close前文件无法删除
  - **解决**：测试中不依赖 `TemporaryDirectory` 自动清理，改用固定路径并在 `teardown` 中移除handlers；生产环境中 `TimedRotatingFileHandler` 的旋转机制本身就是为此设计的
  - **适用场景**：任何在Windows上测试日志/文件输出的场景

- [2026-06-26] 多agent并行开发的依赖管理
  - **现象**：Phase 1(SRT解析) 和 Phase 2(AI客户端) 无相互依赖，可并行开发
  - **原因**：SRT解析只依赖标准库，AI客户端只依赖config，两者通过约定好的文本接口（字符串）解耦
  - **解决**：在 plan.md 中明确标注依赖图，并行启动 dev-agent，缩短开发周期约50%
  - **适用场景**：任何模块化设计的daemon项目，模块间通过纯数据接口（字符串/JSON）解耦时

- [2026-06-26] orchestrator直接执行 vs dev-agent执行的选择标准
  - **现象**：Phase 0（框架搭建）由orchestrator直接执行，其它Phase由dev-agent执行
  - **原因**：Phase 0涉及大量小文件的创建（config.yaml, requirements.txt, .gitignore, __init__.py等），这些文件之间需要一致的命名和结构，orchestrator的全局视角更合适。业务逻辑模块（Phase 1-4）有明确的功能边界，适合分配给独立agent
  - **解决**：框架搭建类任务（项目初始化、配置系统）由orchestrator直接完成；功能模块由dev-agent完成后orchestrator验证集成
  - **适用场景**：所有新daemon项目的启动阶段

## 类别：字幕处理（SRT / WebVTT）

- [2026-06-26] SRT解析的鲁棒性设计 — 三态状态机
  - **现象**：实际SRT文件常有格式异常：空行数不一致、序号缺失、时间戳损坏
  - **原因**：SRT格式无官方严格规范，各种工具产出的文件存在微妙差异
  - **解决**：采用三态状态机（index→timestamp→text）逐行解析，对缺失序号自动生成、对损坏时间戳丢弃重置、对空行静默消费、文件末尾无空行时flush最后条目
  - **适用场景**：任何需要解析 SRTVTT/WebVTT 等字幕格式的项目

- [2026-06-26] 编码检测的BOM优先策略
  - **现象**：中文Windows环境下字幕文件可能是UTF-8、UTF-8-BOM或GBK编码
  - **原因**：不同字幕工具和下载来源使用不同编码
  - **解决**：BOM检测→UTF-8解码尝试→GBK解码尝试→UTF-8+errors=replace 的四级回退。UTF-8检测用4KB采样，处理多字节字符截断边界
  - **适用场景**：任何处理中文文本文件的自动化工具

- [2026-10-01] 多字幕格式支持：内容优先、扩展名兜底的格式识别
  - **现象**：需要在原有 SRT 流程前增加 WebVTT 支持，且下载的字幕经常命名错扩展名
  - **原因**：扩展名不可信（`.vtt` 里可能是 SRT 文本），但只靠内容也不足以判断所有文件
  - **解决**：先按内容嗅探（`WEBVTT` 头 → VTT；逗号毫秒时间戳 → SRT），内容不确定时回退到扩展名；
    两者都不匹配则抛 `UnsupportedSubtitleFormat`。两种格式解析为同一个 `SubtitleEntry` 数据结构，
    下游（AI/写文件）零改动
  - **适用场景**：任何需要支持多种同类容器格式（字幕/日志/表格）的解析器

- [2026-10-30] PyInstaller 打包最疼的两件事：数据根目录与相对路径
  - **现象**：源码跑得好好的，打包后 GUI 能开，但一启动监听就把所有字幕重新处理一遍
  - **原因**：代码按 __file__ 向上找项目根，在冻结应用里指向临时解包目录；配置里的相对路径
    （output/、状态文件）全部落在 exe 目录，导致"历史与去重记录"丢失
  - **解决**：_find_project_root() 增加 sys.frozen 分支（数据根 = exe 所在目录）与
    SRT_DAEMON_HOME 覆盖；输出目录和状态文件在配置里改成**绝对路径**，让命令行版与 GUI 版
    共享同一份历史。GUI 启动时再检查"状态为空但目录里有字幕"并提示
  - **适用场景**：任何从 Python 脚本升级为桌面 exe 的项目

- [2026-10-30] Tkinter 界面在 Windows 高 DPI 下发糊（以及由此产生的"假布局 bug"）
  - **现象**：125% 缩放屏上窗口文字模糊；截图上还出现右侧控件被裁掉
  - **原因**：Tk 默认不是 DPI 感知进程，Windows 把整个窗口位图拉伸；同时 PowerShell 的
    [Screen]::Bounds 返回逻辑像素、Pillow 抓屏返回物理像素，混用后裁错区域
  - **解决**：启动时调用 shcore.SetProcessDpiAwareness(2)（回退 user32.SetProcessDPIAware），
    截图时统一坐标系；布局是否溢出要用 Tk 自己量 winfo_reqwidth 而不是看截图
  - **适用场景**：任何 Tkinter 桌面工具；也适用于"看起来是布局 bug、其实是截图坐标错"的排查

- [2026-10-01] 说话人聚类要单独一条流水线，且必须与 ASR 解耦
  - **现象**：会议要求"按人区分"，但 ASR 只输出文本+时间戳，本身不含说话人信息
    （实测 faster-whisper 1.2.1 的 transcribe() 没有 diarize 参数）
  - **原因**：ASR（说了什么）与说话人聚类（谁说的）是两个独立模型，后者输出的是时间段
  - **解决**：解码一次 16kHz 单声道 WAV，同时喂给 ASR 与聚类器，再用**时间重叠**把说话人贴到文本段上；
    开启词级时间戳时可在词边界切分跨说话人的句子，否则整段归给主导说话人
  - **适用场景**：任何"转录 + 说话人"的需求

- [2026-10-01] 向量聚类后端取舍：sherpa-onnx vs pyannote
  - **现象**：pyannote 是业界标准但模型 gated，需要 HuggingFace 账号+令牌；
    pip install pyannote.audio 会连带 30+ 个包并升级 numpy（2.1.3→2.4.6），
    还会装上 torchaudio 2.11 配 torch 2.9 的错配组合
  - **原因**：pyannote 依赖 pytorch-lightning / optuna / torchaudio 等训练栈，而我们只需要推理
  - **解决**：优先 sherpa-onnx——单个 wheel（2 个包）、不碰 torch/numpy、模型是 GitHub 上非 gated 的
    ONNX（pyannote 分段 + 3D-Speaker 向量，约 44MB）；pyannote 做成可插拔后端，需要更高精度再切
  - **适用场景**：Windows/CPU 环境引入深度学习能力时，优先 ONNX 推理包而不是训练框架

- [2026-10-01] 同一份输入、多种产出形态：内容类型 profile
  - **现象**：访谈、会议、课程的笔记侧重点完全不同（会议要待办和决议，课程要知识结构），
    但处理流水线完全相同
  - **原因**：差异只在"提示词 + 输出结构"，不在解析、AI 调用、写文件这些环节
  - **解决**：把差异抽成 profile（提示词模板 + 文件名关键字），在解析之后、AI 调用之前插一步
    "选择 profile"；解析结果统一成同一种数据结构，下游完全复用。
    选择顺序为 CLI > 文件名 > 内容分类 > 默认，且分类失败必须静默回退，不能拖垮主流程
  - **适用场景**：同一份输入需要按场景产出不同形态文档/报表的流水线

- [2026-10-01] 说话人区分：字幕能做什么、不能做什么
  - **现象**：会议/访谈笔记要求"按说话人区分"，但字幕是纯文本，没有声学信息
  - **原因**：说话人标签只可能来自字幕本身（Teams/Zoom 的 `姓名:`、WebVTT `<v 姓名>`），
    自动字幕（YouTube）通常没有；靠语气"猜"说话人必然有误差
  - **解决**：先用**确定性规则**判断字幕是否带标签（标签至少重复两次且覆盖率 ≥25%，
    或近乎每行都带标签且标签数 ≤6），再据此注入两种不同的指令：
    有标签→严格按标签归属、禁止改名；无标签→占位名 + 必须标注"推测" + 禁止编造姓名。
    另外：只出现一次的说话人不能被过滤掉，否则其发言会被错误归到别人头上
  - **适用场景**：任何需要从文本推断"谁说了什么"的场景

- [2026-10-30] 在线视频转笔记：字幕优先、转写兜底
  - **现象**：URL → 笔记最慢的环节是语音识别（本地 large-v3 约 0.39× 实时，1 小时视频 2.5 小时）
  - **原因**：多数平台其实自带字幕（YouTube 自动字幕免登录即可拿；B站 CC 需 SESSDATA cookie），
    字幕是秒级的
  - **解决**：先把"手动字幕 > 自动字幕 > 下载音频转写"做成三级回退；抓取前用 --dry-run
    列出可用字幕语言，用户能立刻判断会走哪条路。
    注意 B站 多P 在 yt-dlp 里是 playlist，要按 entries 选分P；
    字幕三种格式（VTT/SRT/B站 JSON/YouTube json3）统一转成 WebVTT 再进解析链路
  - **适用场景**：任何"在线内容 → 结构化笔记"的抓取流水线

- [2026-10-30] Windows 控制台默认 GBK，打印中文标题会崩
  - **现象**：print(title) 直接抛 UnicodeEncodeError: 'gbk' codec can't encode character
  - **原因**：中文 Windows 的控制台代码页是 936(GBK)，Python 的 stdout 按它编码；
    视频标题常含 emoji 或生僻字
  - **解决**：CLI 入口先 sys.stdout.reconfigure(encoding='utf-8', errors='replace')，
    日志写入文件不受影响；spawn 子进程时同样设置 PYTHONIOENCODING=utf-8
  - **适用场景**：所有会在 Windows 控制台打印用户数据（标题/文件名/摘要）的脚本

- [2026-10-30] 平台抓取的三类真实失败（实测踩到）
  - **HTTP 567（B站 CDN 风控）**：4 分钟内连续下载 3 个视频后开始被拒；同一视频几分钟前还能下。
    说明这是**IP 级限流**而不是视频问题 → 退避重试（5s/20s）+ 登录 cookies 是唯一稳妥解
  - **空转写**：纯音乐/无人声视频 ASR 返回 0 段，若直接进笔记流水线会抛 traceback。
    必须在转写出口检查"字幕是否有至少一条 cue"，转成清晰的业务错误
  - **浏览器 cookie 读不出**：--cookies-from-browser 在浏览器运行时报
    "Could not copy Chrome cookie database"（Windows 文件锁）。生产路径应该是导出 cookies.txt
  - **适用场景**：任何依赖第三方平台的抓取功能，都要为"限流/空内容/凭据不可用"设计显式错误路径

- [2026-10-30] 让 AI 标注"该截图的位置"要连标记一起设计
  - **现象**：让模型输出截图时间点时，它会估算或编造时间戳，导致抽帧位置全错
  - **原因**：时间戳的可信来源只有输入文本里已有的 [HH:MM:SS]；
    模型自己换算是不可靠的
  - **解决**：三条规则一起写进提示词 —— ①时间戳必须复制自输入中真实出现的
    [HH:MM:SS]；②标记独占一行、格式固定 [[screenshot:HH:MM:SS]]；
    ③宁少勿多、相邻时间点间隔≥60 秒。后处理再兜底：解析失败/超上限/重复/抽帧失败
    的标记一律删除，绝不留占位符
  - **适用场景**：任何"模型给坐标/时间点、程序据此取素材"的功能（截图、切片、跳转链接）

- [2026-11-04] "有没有字幕"不等于"字幕能不能用"
  - **现象**：B站 一个 20 分钟的分P，API 返回 ai-zh 字幕，但只有 51 条、只覆盖前 9%；
    换个时刻再请求，条数变成 131 / 6 条，内容甚至可能来自别的视频
  - **原因**：B站 的 AI 字幕是**按需生成、滚动补齐**的，生成到哪就返回哪；
    CDN 偶发串台（同一个签名 URL 返回其它视频的字幕）
  - **解决**：既要有"合理性校验"（时间戳不能超出视频长度），也要有"**覆盖率门槛**"
    （只覆盖一小部分就视为不可用）；两者都过才用字幕，否则退回本地转写。
    再用 --dry-run 把覆盖率、条数直接打给用户看，避免"笔记只写了开头"的错觉
  - **适用场景**：任何依赖第三方"自动生成字幕/摘要"的能力，都要校验完整性而不只是存在性

- [2026-10-30] customtkinter 三个坑（换界面时实测）
  - **tkraise() 对 CTkScrollableFrame 不生效**：它内部是 canvas + 内层 frame，
    直接 raise 压不住别的页（表现是"切页没反应"）。解法：每页外面包一层普通
    CTkFrame，对包裹层 raise，滚动内容放在里面
  - **geometry 会被 DPI 缩放再乘一次**：进程已经是 DPI 感知时，1180x780 实际变成
    1475×975，在 1080p 屏上被任务栏截断。解法：用 winfo_screenwidth()/scale 反算逻辑尺寸，
    再按 0.86 的余量取高度
  - **子进程执行的入口脚本要自己补 sys.path**：GUI 通过"重新启动自己"跑长任务，
    以脚本方式运行时 sys.path[0] 是 src/srt_daemon，import src.srt_daemon.x 会失败。
    解法：入口文件顶部把项目根插进 sys.path
  - **适用场景**：任何把 ttk/Tk 界面升级到 customtkinter 的桌面工具

- [2026-06-26] 短字幕合并的说话人检测
  - **现象**：讲座/教学视频中同一说话人的句子常被分割为多条短字幕，但对话/访谈中不同说话人不应合并
  - **原因**：语音识别的断句不区分说话人
  - **解决**：基于时间间隔+文本长度+说话人标识符（`- Speaker:` 模式）的三重条件合并策略
  - **适用场景**：处理访谈/对话/多人讨论的字幕

## 类别：AI API调用

- [2026-06-26] API提供商切换的极低成本
  - **现象**：用户要求从 Anthropic Claude 改为 DeepSeek API，修改涉及5个文件
  - **原因**：前期设计将 API 细节封装在 `ai_client.py` 中，config.py提供统一的配置接口，其他模块完全不感知API提供商
  - **解决**：只需修改 `requirements.txt`(依赖)、`.env.example`(密钥名)、`config.yaml`(模型名)、`config.py`(密钥env var名)、`ai_client.py`(SDK调用)。writer/srt_parser/watcher/main 完全不需修改
  - **适用场景**：任何需要支持多AI提供商或将来可能切换提供商的AI集成项目。**核心原则：将SDK细节封装在单一模块，对外只暴露字符串输入输出**

- [2026-06-26] 大文本分块+合并的处理模式
  - **现象**：超长字幕文件（>2000条）可能超出API上下文窗口
  - **原因**：单次调用有token上限，且大文本可能导致响应质量下降
  - **解决**：按字幕条目数分块（非字符数），在SRT块边界切割（不切断单条字幕），每块独立处理后再发送合并请求生成统一文档。代价是增加一次额外的API调用（合并）
  - **适用场景**：任何需要AI处理超长文档的场景（会议记录、视频字幕、长文摘要）

- [2026-06-26] API错误分类与重试策略
  - **现象**：网络不稳定时API调用可能失败，但不应无限重试
  - **原因**：不同类型错误的重试价值不同（429/5xx→重试，4xx→不重试）
  - **解决**：分类处理——RateLimit(429)+ServerError(5xx)+Timeout+Connection→指数退避重试(max 3次，延迟=base*2^(n-1)秒，上限300s)；ClientError(4xx非429)→立即失败
  - **适用场景**：所有调用外部API的daemon项目

## 类别：Windows服务

- [2026-06-26] watchdog + debounce的事件处理模式
  - **现象**：大文件写入可能触发多次文件修改事件，在文件写完前处理会失败
  - **原因**：文件系统事件是即时的，但文件写入是渐进的（尤其大文件或网络驱动器）
  - **解决**：使用 `threading.Timer` 的debounce模式——每次事件取消旧定时器重建新定时器（`delay=2s`），定时器触发时才真正入队处理。`_pending` 字典受 `threading.Lock` 保护
  - **适用场景**：任何需要监听文件写入完成的文件监控场景

- [2026-06-26] watchdog的 `on_moved` 事件使用 `dest_path` 而非 `src_path`
  - **现象**：`FileSystemEventHandler.on_moved` 的目标路径字段命名不直观
  - **原因**：`event.src_path` 是文件旧位置（可能不在监控目录内），`event.dest_path` 是新位置（在监控目录内）
  - **解决**：处理 `on_moved` 时使用 `event.dest_path` 来获取文件在watch目录中的路径
  - **适用场景**：所有使用watchdog库的Python项目

- [2026-06-26] 状态文件的原子写入
  - **现象**：写入过程中断电或崩溃可能导致状态文件损坏
  - **原因**：直接 `write_text` 不是原子操作，中断会留下残缺文件
  - **解决**：先写到 `.tmp` 临时文件，完成后再 `replace(target)`。NTFS上同卷replace是原子操作
  - **适用场景**：任何需要持久化JSON状态的daemon项目

- [2026-06-26] 处理中标记（in-progress）的陈旧清理
  - **现象**：daemon崩溃后重启，之前标记为"处理中"的文件永久被跳过
  - **原因**：崩溃时 `finally` 块未执行，`in_progress` 标记遗留
  - **解决**：启动时检查 `in_progress` 条目的时间戳，超过1小时的陈旧标记自动清除。正常处理完成后立即清除 `in_progress` 标记（在 `_mark_processed` 中）
  - **适用场景**：任何有"处理中"状态追踪的daemon项目
